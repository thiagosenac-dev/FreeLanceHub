FREELANCEHUB - ANOTACOES TECNICAS DO PROJETO
=============================================
Como achar rapido: Ctrl+F na palavra-chave do topico (linha "chaves:").
Caminhos do back a partir de src/main/java/com/senac/freelancehub
Caminhos do front a partir de frontend/app


=====================================================
1. VISAO GERAL
chaves: projeto, roles, perfis, entidades, negocio
=====================================================
- Plataforma de freelance com 3 perfis:
    ROLE_ADMIN    -> gerencia usuarios, clientes e categorias
    ROLE_USUARIO  -> freelancer: escolhe habilidades, ve vagas, envia proposta
    ROLE_CLIENTE  -> pessoa ou empresa: cria projeto, aceita/recusa proposta
- Entidades: Usuario, Cliente, Projeto, Proposta, Categoria, Token
- Entidade principal (CRUD): Projeto -> presentation/ProjetoController.java
- Projeto nasce ABERTO; ao aceitar uma proposta vira CONCLUIDO e as outras
  propostas pendentes do projeto viram RECUSADA.
- Freelancer so ve e so propoe em projeto da categoria que e habilidade dele,
  e so uma proposta por projeto.


=====================================================
2. CAMADAS DDD / CLEAN ARCHITECTURE
chaves: ddd, camadas, pastas, domain, application, infra, presentation
=====================================================
presentation  = Camada de Apresentacao
                controllers REST, recebem a requisicao e devolvem a resposta
                ex: ProjetoController, AuthController
application   = Camada de Aplicacao
                services (orquestram: buscam no banco, chamam a regra da entidade, salvam)
                ports (interfaces dos services) e DTOs (Request / Response)
domain        = Camada de Dominio (o centro, nao depende das outras)
                entities (dados + regras de negocio), valueobject (CPF, CNPJ),
                repository (interfaces JPA), interfaces (IViaCepExternalRepository)
infra         = Camada de Infraestrutura
                configuration (SecurityConfiguration, JwtFilter, Swagger, Cors)
                external (ViaCepExternalRepository) e dto (ViaCepResponse)

Dependencias apontam para dentro: presentation -> application -> domain.
A infra implementa as interfaces do domain.

Frase: "4 camadas: apresentacao, aplicacao, dominio e infraestrutura. Regras no
dominio, services orquestram, camadas conversam por interfaces (portas)."


=====================================================
3. REGRAS DE NEGOCIO NAS ENTIDADES
chaves: regra, regras, entidade, dominio, service
=====================================================
Regra fica na entidade; o service so busca, chama o metodo e salva.

  var projeto = projetoRepository.findById(id).orElse(null);   // busca
  projeto.cancelar();                                          // regra (entidade)
  projetoRepository.save(projeto);                             // salva

Projeto.java   abrir(), validarEdicao(), atualizarDados(), estaDisponivel(),
               clienteAtivo(), pertenceAoCliente(), podeSerAcessadoPor(),
               alterarStatus(), concluir(), cancelar()
Proposta.java  enviar(), validarEdicao(), atualizarDados(), alterarStatus(),
               aceitar(), recusar(), cancelar(), estaPendente(),
               pertenceAoCliente(), pertenceAoFreelancer(), podeSerAcessadaPor()
Usuario.java   validarAcesso(), atualizarDados(), atualizarEndereco(),
               adicionarHabilidade(), removerHabilidade(), temHabilidade(),
               categoriasQuePodeAtender(), tornarAdmin(), excluir(),
               validarEmailDisponivel(), validarSenha(), validarChaveAdmin()
Cliente.java   definirDocumento(), definirEmail(), validarTipo(), validarEmail(),
               cadastrarEndereco(), ativar(), excluir(), alterarStatus()
Categoria.java ativar(), atualizarDados(), alterarStatus(), excluir()

Exemplo (domain/entities/Proposta.java):
  public void cancelar() {
      if (!estaPendente()) throw new IllegalArgumentException("Só é possível cancelar uma proposta pendente!");
      this.status = EnumStatusProposta.CANCELADA;
  }

Regra que depende do banco (ex: uma proposta por projeto): o service so consulta
e passa a resposta; quem decide e a entidade.
  boolean jaEnviou = propostaRepository.existsByUsuario_IdAndProjeto_Id(...);
  proposta.enviar(freelancer, projeto, jaEnviou);

Entidade x service: entidade = dados + regra do proprio objeto (nao conhece banco
nem usuario logado). Service = coordena o caso de uso.

4. VALUE OBJECT
chaves: value object, valueobject, cpf, cnpj
=====================================================
- domain/valueobject/CPF.java e CNPJ.java
- Objeto de valor: representa um valor e se valida no construtor; invalido nem e criado.
  public CPF(String cpf) {
      if (!isValidCpf(cpf)) throw new IllegalArgumentException("CPF Invalido!");
  }
- Validacao: so numeros, tamanho (11 / 14), todos iguais nao, digitos verificadores.
- Usuario tem @Embedded CPF cpf (vira coluna da tabela usuario, sem tabela propria).
- CPF.validarDisponivel() / CNPJ.validarDisponivel() = nao pode repetir.
- Cliente guarda cpf e cnpj como String; empresa usa cnpj (cpf null), pessoa usa cpf
  (cnpj null). Colunas aceitam nulo; quem garante o certo e Cliente.definirDocumento().

5. PORTAS / INVERSAO DE DEPENDENCIA / INVERSAO DE CONTROLE
chaves: ports, portas, interface, inversao, dependencia, controle, autowired
=====================================================
- application/ports/*ServicePort.java = contratos dos services.
- Contrato = interface que so promete os metodos; quem implementa e obrigado a ter.
  public class PropostaService implements PropostaServicePort { ... }
- Controller depende da interface, nao da classe:
  @Autowired
  private PropostaServicePort propostaService;
- Inversao de DEPENDENCIA no domain: domain/interfaces/IViaCepExternalRepository
  (dominio define) e infra/external/ViaCepExternalRepository (infra implementa).
  domain/repository tambem sao interfaces.
- Inversao de CONTROLE: o Spring cria os objetos (@Service, @Component) e entrega
  onde pede com @Autowired; eu nao faco new.

6. BANCO / JPA / RELACIONAMENTOS
chaves: jpa, banco, tabela, hibernate, manytoone, onetomany, manytomany, foreign key, fk
=====================================================
- PostgreSQL, conexao no application.properties (url, username, password).
- Tabelas criadas pelo Hibernate a partir das @Entity: spring.jpa.hibernate.ddl-auto=update
  Cada atributo da classe vira coluna; o nome da classe vira a tabela.
- Repository: interface que extends JpaRepository (save, findAll, findById prontos)
  e consulta pelo nome do metodo: getProjetosByCliente_Id(Long cliente)

Relacionamentos (domain/entities):
  Projeto  -> Cliente   @ManyToOne  coluna cliente_id   (cada cliente ve os seus)
  Projeto  -> Categoria @ManyToOne  coluna categoria_id
  Proposta -> Projeto   @ManyToOne  coluna projeto_id   (aceitar recusa as outras do projeto)
  Proposta -> Usuario   @ManyToOne  coluna usuario_id   (freelancer que enviou)
  Usuario  -> Cliente   @ManyToOne  coluna cliente_id
  Usuario  -> Proposta  @OneToMany(mappedBy = "usuario")
  Cliente  -> Projeto   @OneToMany(mappedBy = "cliente")
  Usuario <-> Categoria @ManyToMany tabela tb_habilidade (usuario_id, categoria_id)
  Token    -> Usuario   @ManyToOne
- mappedBy = o outro lado guarda a chave estrangeira.
- ManyToMany igual ao Aluno/Curso (matricula) da aula.

Exclusao logica: nao apaga, troca status (ATIVO, BLOQUEADO, EXCLUIDO / CANCELADO).

8. SEGURANCA / JWT / TOKEN
chaves: token, jwt, login, bearer, jwtfilter, security, hasrole, 401
=====================================================
Login (caminho):
  AuthController @PostMapping("/login")
   -> UsuarioService.validarUsuarioAutenticadoRetornaToken (confere email/senha,
      usuario.validarAcesso() barra bloqueado/excluido)
   -> TokenService.gerarToken: JWT.create() com emissor, email, UUID, expiracao,
      assinado HMAC256 com spring.secretkey; salva o token no banco
   -> devolve LoginResponse(token, role)
- Banco guarda: token + usuario. Front recebe: token + role.

Cada requisicao (infra/configuration/JwtFilter.java):
  String token = authHeader.replace("Bearer ", "");
  var usuarioLogado = tokenService.verificarToken(token);  // assinatura, validade, existe no banco
  SecurityContextHolder.getContext().setAuthentication(user);
  falhou -> 401 "Token invalido"
- Bearer = palavra padrao antes do token no header Authorization.
- Rotas livres: lista no JwtFilter + permitAll() no SecurityConfiguration
  (/auth/login, /auth/registrar, /auth/registrar-cliente, /endereco, /publico,
   /usuarios/admin, POST /categorias, swagger).
- Permissao por perfil: hasRole / hasAnyRole no SecurityConfiguration.
- Token no banco = da para invalidar.
- @Bean CommandLineRunner limpaTokens (FreeLanceHubApplication.java): roda ao iniciar
  o back e faz tokenRepository.deleteAll() -> reiniciar derruba os logins.
- @Bean = o Spring roda o metodo e guarda o objeto (filterChain, customOpenAPI, limpaTokens).

Desligar seguranca (teste 2) - mexer nos DOIS:
  SecurityConfiguration -> colocar "/**" na lista do permitAll()
  JwtFilter             -> colocar || uri.startsWith("/") no if das rotas livres
  (JwtFilter e @Component, roda mesmo comentando o addFilterBefore)
  Testar GET /usuarios ou GET /categorias sem token. Depois desfazer.

9. MULTIUSUARIO
chaves: multiusuario, multilocacao, cliente_id, ehDoUsuario, 404, filtro
=====================================================
- UsuarioLogado (application/DTOs) vem do token: id, email, cpf, cliente_id, role.
  O JwtFilter monta com usuario.getCliente().getId().
- Listagem (ProjetoService.ListarTodosProjetosGrid):
  admin -> findAll(); cliente -> getProjetosByCliente_Id(usuarioLogado.cliente_id())
- Buscar/editar/excluir: ehDoUsuario -> projeto.podeSerAcessadoPor(ehAdmin, clienteId)

- Proposta: proposta.podeSerAcessadaPor(ehAdmin, clienteId, usuarioId)
  (cliente ve as dos projetos dele, freelancer so as que enviou).

12. FLUXOS COMPLETOS (FRONT ATE O BANCO)
chaves: fluxo, caminho, passo a passo, rota
=====================================================
Padrao: tela -> service do front -> api.ts (axios + token) -> JwtFilter ->
        controller -> porta -> service -> entidade (regra) -> repository -> banco

CRIAR USUARIO (admin)
  (sistema)/usuarios/novo -> UsuarioForm.tsx salvarUsuario(usuario)
  -> services/usuarioService.ts api.post('/usuarios', usuario)
  -> UsuarioController @PostMapping criar -> UsuarioServicePort
  -> UsuarioService.salvarUsuario(request, 0L) -> usuarioNovo.tornarAdmin()
  -> usuarioRepository.save -> UsuarioResponse

CADASTRO DE CLIENTE (publico)
  registrar-cliente/page.tsx handlerRegistrar -> authService.registrarCliente
  -> api.post('/auth/registrar-cliente', dados)  (sem token)
  -> AuthController registrarCliente -> UsuarioServicePort -> UsuarioService.registrarCliente
  -> Cliente.validarTipo, cliente.definirDocumento, cliente.cadastrarEndereco ...
  -> clienteRepository.save(cliente) + usuarioRepository.save(usuarioCliente)
  Pessoa/empresa no front: botoes "Sou pessoa"/"Sou empresa" -> setTipoCliente,
  ehEmpresa troca os campos (razao social + CNPJ ou CPF).

EXCLUIR PROJETO
  (sistema)/projetos/page.tsx excluirProjeto -> projetoService.deletarProjeto
  -> api.delete('/projetos/' + id + '/excluir')
  -> ProjetoController @DeleteMapping("/{id}/excluir") -> ProjetoService.excluir
  -> ehDoUsuario -> projeto.cancelar() -> projetoRepository.save (exclusao logica)

ENVIAR PROPOSTA
  (sistema)/propostas/components/PropostaForm.tsx salvarProposta(proposta, projetoId)
  -> services/propostaService.ts api.post('/propostas', { ...proposta, projetoId })
  -> PropostaController criar -> PropostaService.salvarProposta(request, 0L)
  -> proposta.enviar(freelancer, projeto, jaEnviou) -> propostaRepository.save

ACEITAR PROPOSTA
  PATCH /propostas/{id}/status -> PropostaService.atualizarStatus
  -> proposta.aceitar(outrasDoProjeto): aceita, recusa as pendentes, projeto.concluir()
  -> saveAll das recusadas + save do projeto e da proposta

13. FRONT: ESTRUTURA, LAYOUTS, COMPONENTES
chaves: next, spa, layout, multilayout, landing, componente, components, rotas
=====================================================
- Next + TypeScript, SPA (troca de tela sem recarregar, router.push / Link).
- Rotas por pasta: pasta com page.tsx vira pagina. (pasta) nao entra na URL.
  [codigo] = rota dinamica (id na URL, useParams).
- Landing page: app/page.tsx (rota /), publica; usa components/ProjetosPublicos.tsx (/publico).
- Multi layout:
  app/layout.tsx           -> raiz, so envolve com <StoreProvider>
  app/(sistema)/layout.tsx -> le usuario do Redux; null -> router.push("/login");
                              com usuario -> Sidebar + Header + pagina + Footer
- Componente = parte da tela reaproveitada (funcao que devolve JSX).
  components/ (Header, Sidebar, Footer, ProjetosPublicos) usados no (sistema)/layout.tsx:
    import Sidebar from "../components/Sidebar";   <Sidebar />
  Forms: projetos/components/ProjetoForm.tsx usado em novo, editar e ver.
- Sidebar por perfil: cada link tem perfis: ["ROLE_ADMIN", ...]
    const role = useSelector((state: RootState) => state.auth.usuario?.role);
    links.filter(link => link.perfis.includes(role))
  role nasce no back (LoginResponse) -> login grava no Redux -> Sidebar le.
- Hooks (funcoes use...): useState (dado da tela), useEffect (roda ao abrir),
  useSelector (le Redux), useDispatch (grava Redux), useRouter (troca pagina),
  useParams (id da URL).
- Erros: so o 401 e global (api.ts). 403/400/404 caem no try/catch da pagina (alert).

14. REDUX
chaves: redux, store, slice, reducer, dispatch, useselector, provider, categorias
=====================================================
Pasta: app/redux
  store.ts           configureStore({ reducer: { auth: authReducer, categorias: categoriasReducer } })
  slices/authSlice.ts       estado { usuario, token }; reducers login, logout
  slices/categoriasSlice.ts estado { lista }; setCategorias, limparCategorias;
                            extraReducers escuta o logout e limpa a lista
  StoreProvider.tsx  <Provider store={store}> usado no app/layout.tsx
- Store = junta tudo. Slice = uma parte (assunto + reducers). Reducer = funcao que muda o estado.
- dispatch GRAVA, useSelector LE, useState = memoria so da tela.
- Token e usuario SO no Redux (sem cookie): F5 limpa e volta para o login (pedido do PDF).

Onde usa:
  login/page.tsx              dispatch(login({ token, usuario: { ...usuarioLogado, role } }))
  components/Sidebar.tsx      useSelector(state => state.auth.usuario?.role)
  (sistema)/layout.tsx        useSelector(state => state.auth.usuario)
  components/Header.tsx       handlerSair -> dispatch(logout())
  services/api.ts             store.getState().auth.token / store.dispatch(logout())
  (sistema)/projetos/page.tsx dispatch(setCategorias(await buscarListaCategorias()))
  projetos/components/ProjetoForm.tsx useSelector(state => state.categorias.lista)

=====================================================
- app/services: cada funcao chama um endpoint do back; a tela so chama a funcao.
  export async function buscarListaProjetos() {
      const dados = await api.get<Projeto[]>("/projetos");   // ProjetoController.ListarTodos

    const token = store.getState().auth.token;
